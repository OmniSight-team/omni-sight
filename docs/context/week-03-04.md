## OMNI-300 · Datasets: native layout, local subset, one clip through the app

### Why this ticket exists

Slice 6 loads three datasets through the normal pipeline and derives the lead-up
windows the forecasting model trains on. Its loaders need a written
specification of where every video and every label lives. The ticket started life
as a sprint-2 carry-over asking for a flat layout — each clip's annotation beside
its video, same base name — and was rewritten on 2026-09-21 once the datasets were
actually on disk and it was clear none of them are shaped that way.

### What was done

Work ran 2026-09-20 → 21. All downloading and extraction happened **in Colab,
writing straight to Google Drive** (`MyDrive/omnisight/data/`), not on the laptop:
Colab's network is far faster than a home connection, Drive has 5 TB free, and
Colab mounts Drive for the encoding and training work later anyway. The laptop
only receives a small subset.

#### UCF-Crime — 96 GB, 1,950 videos

**Source:** the official Dropbox folder linked from
<https://www.crcv.ucf.edu/projects/real-world/>. The folder was read directly
before downloading, because the file list first assumed from the project page
was wrong: training normals are **two** archives (35.46 + 31.68 GB), and
`Normal_Videos_for_Event_Recognition.zip` and `Anomaly_Train.txt` had been
missed entirely. Twelve files in total.

**Download:** `wget -c` against each file's Dropbox share link with `dl=1`, in
stages (annotations, then anomalies and test normals, then training normals) so a
dropped Colab runtime never cost more than one file. Every on-disk size matched
the Dropbox listing exactly — Dropbox reports GiB, so 6,272,044,173 bytes appears
as "5.84 GB".

**Extraction:** each archive's structure was inspected with `zipfile` before
writing anything. Every archive has its own single top-level folder, all eight
different, so extracting straight into `videos/` was collision-free. Each extract
printed its mp4 count against the count from inspection:

| Archive | mp4 | Check |
|---|---|---|
| Testing_Normal_Videos | 150 | OK |
| Anomaly-Videos-Part-1 | 200 | OK |
| Anomaly-Videos-Part-2 | 200 | OK |
| Anomaly-Videos-Part-3 | 350 | OK |
| Anomaly-Videos-Part-4 | 200 | OK |
| Normal_Videos_for_Event_Recognition | 50 | OK |
| Training-Normal-Videos-Part-1 | 430 | OK |
| Training-Normal-Videos-Part-2 | 370 | OK |

13 anomaly classes present, 1,950 videos total. Zips deleted only after every
count matched.

#### VIRAT — 37.6 GB, 329 videos

**Source:** the Kitware data portal, which is public — no account or form,
contrary to what the dataset notes had said. Four archives, `videos-00/01/04/05`.
The gap in numbering looked like missing files; it is not. The numbers are
scene-ID groups (`VIRAT_S_00xxxx`, `01xxxx`, `04xxxx`, `05xxxx`) and no scene ID
starts with `02` or `03`. The per-archive listings were read to confirm this
before downloading.

**Extraction:** the first unzip run was interrupted and `videos-00.zip` returned
an error. Re-extracted on its own with `-o`; the folder then held the expected
329.

**Verification:** `md5sum -c viratdata.sums.txt` — **1,236 OK, 0 FAILED.** A first
run of the check reported every file as *FAILED open or read*; that was because it
ran before extraction, against paths inside the zips. Not corruption.

## OMNI-301 · Carry-over: retention default

### Why this ticket exists

`videos.retention_until` was created in OMNI-202 but nothing ever wrote to it, so
every row was `NULL`. Slice 16 builds the job that deletes expired footage; with an
empty column that job has nothing to act on and slice 16 would start by fixing
slice 2. An hour now avoids that. The ticket was trimmed on 2026-09-21 to the
retention default alone — the sprint-2 docs and pull-request items it originally
carried are no longer in it.

### What was done

Done 2026-09-21. First checked the ticket's "state found" claim against the code:
`retention_until` appeared only in `models.py`, the response schema, and the
`_to_detail` mapping in `videos.py`, and no setting or `.env.example` key existed.
The claim was right.

#### Step 1 — a retention setting

`services/query/app/settings.py` gained:

```python
# ge=1: the slice-16 retention job deletes footage past this date, so a
# zero or negative value would mark every new upload as already expired.
video_retention_days: int = Field(30, ge=1)
```

The `ge=1` is beyond what the ticket asked for; it is there because a `0` or a
negative value would silently make every new upload expire on arrival, and the job
that acts on it deletes files. `.env.example` gained `VIDEO_RETENTION_DAYS=30` with
a comment saying what it controls. A search for a bare `30` in `services/query/app/`
and `scripts/` finds only that default.

#### Step 2 — set it on every new recording

In `POST /videos/upload`, `created_at` and `retention_until` now come from **one**
Python timestamp and go into the same INSERT:

```python
created_at = datetime.now(UTC)
video = Video(
    ...,
    created_at=created_at,
    retention_until=created_at + timedelta(days=settings.video_retention_days),
)
```

`created_at` used to be a database default (`server_default=now()`). Setting it in
Python instead is what makes "exactly `created_at` plus N days" true by
construction, independent of the database's timezone. One INSERT means no row can
exist without a retention date. The upload is the only place a `Video` row is
created today; slice 4's camera recordings will need the same treatment.

#### Step 3 — backfill

`scripts/backfill_retention.py` runs one `UPDATE videos SET retention_until =
created_at + <days> WHERE retention_until IS NULL`, so a row that already has a
date is never touched — that is what makes it idempotent. It prints how many rows
it changed. Run against the three rows uploaded for OMNI-300 (all `NULL`):

| Run | Rows updated |
|---|---|
| 1 | 3 |
| 2 | 0 |

`SELECT count(*) FROM videos WHERE retention_until IS NULL` went **3 → 0**, and
every row's `retention_until - created_at` is exactly `30 days`.

One behaviour to know about: the date is counted from each row's own `created_at`,
not from today, so a recording older than 30 days comes out already expired and the
slice-16 job will treat it that way. Nothing in the dev database is that old. The
script's docstring says so.

#### Step 4 — tests

`services/query/tests/test_video_retention.py`, three tests, same setup as
`test_video_upload.py` (temp storage directory, probing stubbed to "ingestion
unavailable", a throwaway operator account created and deleted):

- an upload's `retention_until` equals `created_at + timedelta(days=
  settings.video_retention_days)` exactly
- with `video_retention_days` monkeypatched to `7`, a new upload gets 7 days —
  proving the number comes from settings, not a literal
- `GET /videos/{id}` returns a non-null `retention_until`

`uv run pytest` — **65 passed** (62 before, 3 new). The backfill was run *before*
the suite on purpose: the existing upload tests clean up with
`session.query(Video).delete()`, which empties the whole `videos` table in the dev
database, so running pytest first would have deleted the very rows the backfill
needed to be shown on. It did delete the three OMNI-300 demo uploads afterwards.

### Two small detours

- `ruff` flagged the new script's imports as unsorted (`I001`, because the
  `sys.path` insert has to come before the `app.*` imports); fixed with
  `ruff --fix`. The other findings in `videos.py` are the `B008` `Depends(...)`
  pattern already present throughout `services/query/app`
- The first attempt at a live upload found the browser session gone: tokens
  expire after 15 minutes of inactivity (NFR-9), which is the feature working.
  Checked the running `query` container instead (it had hot-reloaded, read
  `video_retention_days = 30`, and contained the new upload code), then repeated
  the upload once signed in again

### Verification performed

- Backfill: 3 rows `NULL` → run 1 updates 3 → run 2 updates 0 → `IS NULL` count 0;
  gap on each row exactly 30 days
- `uv run pytest`: 65 passed; `ruff` clean on every file this ticket touched
  apart from the pre-existing `B008` findings
- **Live, through the Video Archive screen:** `000413.mp4` landed `ready` (row 68)
  with `created_at` 2026-09-21 12:17:15 UTC and `retention_until` 2026-10-21
  12:17:15 UTC — exactly 30 days apart, from the running container

### Result

- `VIDEO_RETENTION_DAYS` (default 30, minimum 1) is the one place the period is
  set; every new upload is stamped with `created_at + that many days` in the same
  INSERT, and existing rows can be filled by an idempotent script
- The column slice 16 needs is populated for every row that exists today
- All checklist items in OMNI-301 are ticked in `docs/tickets/week-03-04.md`

Committed together with the OMNI-300 step-4 notes as `636cc99`.

## OMNI-302 · Segments and camera_stats tables

### Why this ticket exists

**FR-3** — store each analysed segment with its details (time, source camera,
representative image) for later retrieval. Everything else in this sprint writes to
or reads from these tables: OMNI-303 creates segment rows, 304 fills
`motion_score`, 306 re-gates them from disk, 307–310 serve them to the screens, and
Part B writes live frames and counters into them. Getting the shape and the
nullability right now avoids a second migration mid-sprint.

### What was done

Done 2026-09-21, on `slice-03-04-frames-live`. Before designing anything, read the
tickets that will use the tables (OMNI-303 to 307), because the ticket asks for two
nullability decisions "now" and they only make sense against what comes next.

#### Step 1 — the model and the shared enum

The ticket's `source_type in {upload, camera}` became a new shared enum,
`SegmentSourceType`, in `services/common` beside the other four (one file each,
exported from `__init__.py`). It is deliberately **not** `VideoSource`, which has a
third value, `dataset`: dataset footage goes through the normal upload path (the
OMNI-300 step 4 result), so a segment never needs that value.

`Segment` and `CameraStats` were added to `services/query/app/models.py`:

| Column | Decision | Reason |
|---|---|---|
| `video_id` | nullable, FK to `videos`, `ON DELETE CASCADE` | a live frame has a camera but no uploaded file; the cascade takes the rows with the video |
| `camera_id` | nullable, FK to `cameras`, no cascade | an upload has no camera; a camera with live frames must be disabled, not deleted |
| `frame_path`, `thumb_path` | NOT NULL | OMNI-303 writes both for every frame and OMNI-306 re-gates "from the frames already on disk" |
| `motion_score` | nullable | NULL means "not scored yet"; cheaper to allow now than to migrate later |
| `admitted` | NOT NULL, default false (in the database too) | as the ticket asks |
| `source_type` | NOT NULL, `SegmentSourceType` | as the ticket asks |

One addition the ticket did not ask for: a `CHECK (video_id IS NOT NULL OR
camera_id IS NOT NULL)`. With both columns nullable, nothing else stops a segment
that came from nowhere.

`camera_stats` has `camera_id` as its primary key and foreign key with
`ON DELETE CASCADE` (counters mean nothing without their camera), `captured` and
`dropped` as `BIGINT` defaulting to 0, and a nullable `last_frame_at`.

#### Step 2 — one migration, both indexes

`alembic revision --autogenerate` produced revision `2424eac9d88a` with both tables,
the `CHECK`, the two foreign keys' cascade settings and both indexes,
`(video_id, timestamp_s)` for slice 8's time queries and `(camera_id,
timestamp_s)` for Part B's live frames. The generated file needed no edits to match
the design, except one, found by testing:

**The downgrade leaves the enum type behind.** `drop_table` does not drop
`segment_source_type`, so `upgrade` → `downgrade -1` → `upgrade` failed with
*type "segment_source_type" already exists*. Fixed by adding
`op.execute("DROP TYPE IF EXISTS segment_source_type")` to `downgrade()`. The
earlier migration (`62326bb11aff`) has the same gap for its own enums and was left
alone; it only matters if someone downgrades past it.

Proof of "applies on a fresh database" without wiping the dev data (`down -v` would
delete every upload and account): created a throwaway database `omni302_fresh` in the
same Postgres, pointed the migration at it with `POSTGRES_DB`, and ran all three
revisions from empty, then downgrade, then upgrade again, and dropped it. `\d
segments` and `\d camera_stats` showed the intended columns, defaults, indexes,
check and foreign keys. The real dev database was then upgraded to the new head, and
`alembic check` reports no difference between the models and the migration.

#### Step 3 — deleting a video deletes its segments and their files

The database cascade removes the rows, but the frame and thumbnail files are on the
volume, which SQL cannot touch. `delete_video` in `services/query/app/videos.py` now
reads every segment's `frame_path` and `thumb_path` first, deletes and commits the
row (the same order OMNI-207 chose: the database is what every endpoint trusts, so
it is never left claiming something that is gone), then unlinks the video file and
all the segment files. A file that is already missing is ignored, and any other
failure to remove one is logged, not raised.

#### Step 4 — two gaps the new foreign keys would have opened

Neither is in the ticket, both would have shown up as an unexplained 500 in Part B:

- `DELETE /cameras/{id}` (OMNI-203) only checked for a *video* referencing the
  camera. A camera with live segments and no video would now hit the new
  `segments.camera_id` foreign key. `delete_camera` in
  `services/query/app/cameras.py` now treats a stored segment like a recording and
  disables the camera instead
- `camera_stats` would have blocked the same delete, hence its `ON DELETE CASCADE`

#### Step 5 — tests

`services/query/tests/test_segments.py`, 8 tests: `admitted` defaults to false
(raw `INSERT` that never mentions it, so it is the database's default being tested);
an upload segment needs no camera and a live segment needs no video; a segment with
neither is rejected; deleting a video removes its segment rows and all seven of its
files while a **second video's** rows and files are untouched; deleting still
succeeds when a segment file is already gone; a camera with only live segments is
disabled, not deleted; `camera_stats` counters start at 0; the stats row goes with
its camera.

The delete test was checked by breaking the code: with the segment-file removal
temporarily disabled it failed on the leftover files, and it passed again once
restored. All 8 had passed first time, which on its own proves little.

### Verification performed

- Migration from empty on a scratch database, downgrade, re-upgrade (the last step
  is what found the enum bug); `alembic check` clean on the real database
- `uv run pytest` — **73 passed** (65 before, 8 new); `ruff` clean on every file
  this ticket touched apart from the `B008` pattern already present. It flagged

## OMNI-303 · Frame extraction with thumbnails

### Why this ticket exists

Everything visible in this sprint — the frame grid, the playback markers, the
threshold slider — is built on rows that this ticket creates: one segment per
sampled frame, with a full frame and a thumbnail on disk. It is also where the
sprint's central design decision becomes real code: **one function that turns a
frame into a segment and knows nothing about where the frame came from**, so that
Part B's live worker can call the same thing.

### What was done

Done 2026-09-21 on `slice-03-04-frames-live`. Ingestion and query both have a
top-level package called `app`, which shaped how the work was split and tested
(see step 1).

#### Step 1 — `process_frame()` first

`services/ingestion/app/pipeline.py` holds `process_frame` and the file extraction
loop that calls it. `process_frame(frame, source, gate, frames_dir, thumbs_dir, …)`
takes a decoded frame, a `FrameSource` (source type, frame index, timestamp, video
id, camera id), a gate, and the two output directories; it runs the gate, writes
the frame and thumbnail, and returns a `SegmentRecord`, which is the fields of a
`segments` row. Nothing in it says whether the frame came from a file or a camera:
the caller supplies the directories, so a live frame simply gets a different one.
A test calls it with a synthetic frame labelled `camera`, no video, camera 3, and
it works.

Two design points:

- **The gate is a seam, not an algorithm yet.** `FrameGate.evaluate()` currently
  returns "not scored, not admitted", so every segment says honestly that no
  decision has been made about it (`motion_score` NULL, `admitted` false). It is
  passed in rather than created inside because OMNI-304's motion detection compares
  a frame with earlier ones and so has to carry state between calls. 304 replaces
  the body; `process_frame`'s signature does not change
- **`pipeline.py` imports nothing from `app.*`.** Every setting arrives as an
  argument. That is what allows its tests to load it by file path
  (`importlib`) under their own name, so the ingestion suite and query's can run in
  the same pytest session despite both having a package called `app`

#### Step 2 — extraction at a configurable interval

`extract_file` steps through the video with `grab()`, which decodes without
converting the frames it skips, and `retrieve()`s only every `interval_s` seconds.
Frame `i` is sampled when `i >= round(k * interval_s * fps)` for the k-th sample;
`timestamp_s` is `frame_index / fps`, the same arithmetic the probe uses for
duration. An interval shorter than one frame cannot stall the loop (it steps at
least one frame). It reads until the file actually ends rather than trusting the
container's frame count.

The interval and the other knobs are ingestion settings, read from `.env`:
`EXTRACT_INTERVAL_S` (default **1.0**, must be above 0), `thumb_width_px` (320),
`frame_jpeg_quality` (85), `thumb_jpeg_quality` (70). `EXTRACT_INTERVAL_S` was
added to `.env.example` with a comment, as `VIDEO_RETENTION_DAYS` was in OMNI-301.

**The interval chosen: one frame per second, and why.** Ten minutes is then 600
frames plus 600 thumbnails. Measured on real dataset clips with the default
settings:

| Clip | Segments | Frame KB | Thumb KB | KB per segment | 10 min at 1 fps |
|---|---|---|---|---|---|
| CCD 640×360, 10 fps | 5 | 18.1 | 5.5 | 23.6 | 14 MB |
| UCF-Crime 320×240, 30 fps | 13 | 10.4 | 7.7 | 18.1 | 11 MB |
| VIRAT 1280×720, 23.97 fps | 20 | 132.6 | 9.3 | 141.9 | 83 MB |

The full-size frame dominates the cost and grows with resolution; the thumbnail is
about 6–9 KB whatever the source. At one frame per second the disk cost is
tolerable even for 720p, while a person or vehicle crossing a scene still shows up
in several consecutive frames. This is a judgement, not something tuned against
detection quality. The case it serves worst is CCD: a 5-second clip gives only 5
segments, so the CCD clips (4,500 of them, about 0.5 GB of frames and thumbnails
at 23.6 KB each) may want a smaller interval when they are loaded in slice 6. That
is why it is a setting. The sentence for the report is: *one frame per second,
because it keeps a ten-minute recording to about 600 frames (roughly 10–80 MB
depending on resolution) while still catching activity that lasts more than a
second or two.*

#### Step 3 — thumbnails small enough for a grid of two hundred

Thumbnails are JPEG at width 320 with the aspect ratio kept, quality 70, and are
never upscaled (a frame narrower than 320 keeps its size). On the live 640×360
clip they came out at 6.0–6.9 KB each, so two hundred is about 1.3 MB. That clip is
a synthetic test pattern that compresses well; the dataset clips above (5.5–9.3 KB)
are the realistic figure. Whether two hundred of them *load without a stall* in the
browser is OMNI-307's acceptance and was not tested here.

#### Step 4 — the layout on the shared volume

`/data/frames/{video_id}/000000.jpg` and `/data/thumbs/{video_id}/000000.jpg`,
named by the frame's index in the source video, zero-padded to six digits. The two
root paths are in `CommonSettings` (`frames_path`, `thumbs_path`) rather than in
either service, because ingestion writes the folders and query deletes them and the
two must never disagree.

Two **new named volumes**, `frame_storage` and `thumb_storage`, are mounted into
both `query` and `ingestion` in `docker-compose.yml`. They are separate on purpose:
OMNI-307 serves thumbnails through Nginx straight off the volume, and that should
not expose full-resolution frames. **`docker compose up -d` has to recreate the
containers once to pick the volumes up** (bind-mounted code hot-reloads; new
volumes do not).

#### Step 5 — background, `extracting` → `ready`

`POST /videos/{id}/extract` returns **202 immediately** with `{video_id, status:
"extracting"}`; `GET /videos/{id}` is how a client sees progress. The ticket sketches
the response as `{segments_created}`, which cannot be both immediate and
background, so it is not literal: the count is `segments_count` on the detail
response. That field had been hard-coded to 0 since OMNI-206 ("slice 3 fills it");
it is now a real count, and the list endpoint gets its counts with one grouped
query per page rather than one per row.

Who does what: **query owns the database, ingestion owns the decoding.** The
endpoint claims the video with one conditional `UPDATE ... WHERE status IN (ready,
failed)`, so two requests at once cannot both start; a video that is already
`extracting`, or is still `uploaded` (not yet probed), gets a 409 with the reason,
a missing one a 404. A FastAPI background task (`app/extraction.py`) then asks
ingestion's new `POST /extract/file` to cut the frames and stores the result. The
new ingestion route is a plain `def`, so the blocking decode runs in the
threadpool.

#### Step 6 — a failure leaves `failed` with a reason, never a stuck `extracting`

The reason has to be stored, because the request that started the job has long
since returned. `videos` had no column for it, so a second small migration,
`1f12c0d52cea`, adds `videos.error` (nullable text); `GET /videos/{id}` returns it.

Every path ends in `failed` with an `error`: ingestion reports a bad file (missing,
cannot be opened, cannot decode frame N); ingestion is unreachable ("ingestion
service unavailable"); ingestion's answer is malformed and no row can be built; or
anything unexpected raises inside the job (a catch-all, so nothing can escape and
leave the video `extracting`). On a failure ingestion deletes the files it had
written, and on an insert failure query removes the folders, so a failed
extraction leaves no files and no rows. Rows and status are written in **one
transaction**: a video has all its segments or none.

Two cases the ticket did not spell out:

- **A restart mid-extraction.** The background task dies with the process, so the
  video would stay `extracting` forever. On startup query now marks any video left
  `extracting` as `failed` ("extraction was interrupted by a restart") in its
  lifespan hook. This also fires on a dev auto-reload, which is right, because
  the reload kills the task too
- **Deleting a video mid-extraction** would let the job write frames for a video
  that no longer exists, so `DELETE /videos/{id}` returns 409 while it is
  `extracting`

#### Step 7 — re-running replaces

Before asking ingestion, the job deletes the video's existing segment rows and
their files, and ingestion wipes the video's two folders at the start of every
extraction (they are that one video's, so anything in them is stale, including
leftovers of a crash). The order matters: if a re-run fails, the video has no
segments rather than segments whose files ingestion has already overwritten.

This also closes the gap OMNI-302 left: `delete_video` now removes the video's
frame and thumbnail **folders**, not just the files. The removal code is shared
(`remove_segment_files` in `extraction.py`) between delete and re-extraction.

### Verification performed

## OMNI-304 · Algorithm 1 — motion gating

### Why this ticket exists

**FR-1b** and, per the ticket's own line, the heart of the sprint: everything
built so far stores a frame regardless of content; this is what decides which
frames are actually worth looking at. `process_frame()` (OMNI-303) already has a
`gate` seam built for exactly this — `FrameGate.evaluate()` returning "not
scored, not admitted" — so this ticket's job is to give that seam a real
implementation without touching its signature.

No Phase A book file exists in this repo, so the algorithm's four numbered steps
in the ticket itself are the specification worked from directly.

### What was done

Done 2026-09-23 on `slice-03-04-frames-live`.

#### Step 1 — implemented inside `process_frame()`, via the existing gate seam

`MotionGate(FrameGate)` in `services/ingestion/app/pipeline.py`. `process_frame()`
itself is unchanged — it already calls `gate.evaluate(frame)` and stores whatever
`GateDecision` comes back. `main.py`'s extraction route builds one `MotionGate`
per request, from settings, and passes it to `extract_file`. One gate per
extraction, never shared or reused across videos, because it holds a buffer of
earlier frames as state — a second video must start with an empty buffer, not the
tail of the first (tested: `test_a_fresh_gate_per_video_carries_no_state_from_a_previous_one`).

#### Step 2 — the four steps, and the two design decisions the ticket left open

1. **Compare against an earlier buffered frame.** A `deque(maxlen=buffer_frames)`
   holds the last N *sampled* frames (grayscale, blurred — see step 4). Once it is
   full, the current frame is compared against `buffer[0]`, the oldest entry —
   `buffer_frames` samples back — and *then* the current frame is appended, which
   evicts that same oldest entry automatically. `buffer_frames` has a floor of 2
   in settings: at 1 the "buffered" frame would be the one immediately before,
   which is exactly what the ticket says not to compare against
2. **Grid.** `np.array_split(diff, grid_size, axis=0/1)`, not a fixed cell size —
   it tolerates a resolution that doesn't divide evenly by `grid_size` (some cells
   end up a pixel larger) instead of assuming one that happens to. Tested on a
   203×203 frame against `grid_size=4`
3. **Count cells showing meaningful change.** A cell's mean absolute difference
   (0-255 grayscale) has to exceed `cell_threshold` to count. This is the design
   decision the ticket doesn't spell out: "threshold" in the ticket's checklist
   names *this* per-cell bar, separate from the count of cells needed to admit
4. **Admit above a threshold.** `admitted = active_cells >= min_active_cells`,
   the second, separate bar. `motion_score` is the raw active-cell count itself
   (a float, e.g. 3.0 of 64 for the default 8×8 grid) — not a normalized
   fraction — because the ticket's acceptance criterion asks for numbers that
   "tell the story without explanation," and a plain count against a plain
   threshold is the more direct of the two to read

Settings (`services/ingestion/app/settings.py`, `.env.example`, and the real
`.env`, matching the pattern from OMNI-301/303): `motion_grid_size` (default 8),
`motion_cell_threshold` (25.0), `motion_min_active_cells` (3), `motion_buffer_frames`
(5, floor 2), `motion_blur_kernel` (21, must be odd — a Pydantic field validator
rejects an even value at settings-load time). No literal appears in `pipeline.py`
itself; every number is a constructor argument, supplied by `main.py` from
settings, the same rule `pipeline.py` already followed in OMNI-303.

**A gap found while adding `.env`:** `EXTRACT_INTERVAL_S` (OMNI-303) was in
`.env.example` but had never actually been added to the real `.env` — it worked
anyway, because the setting has a Python default, but it was inconsistent with
`VIDEO_RETENTION_DAYS`, which OMNI-301 did add to both. Fixed alongside the new
motion keys.

#### Step 3 — `motion_score` stored on every segment, admitted or not

Structurally already true from OMNI-303 (`process_frame` always writes both
fields of the `GateDecision` it gets back), so this box is about the gate itself
never special-casing a low score into `None`. It only returns `None` while the
buffer has not yet filled — genuinely "not scored yet," the same meaning that
value already carried before this ticket — and a real number, however low, for
every frame after that. A below-threshold frame's score (e.g. `0.0`) is written
and kept exactly like an admitted one; nothing is dropped.

#### Step 4 — grayscale and blur before differencing

`cv2.cvtColor(frame, COLOR_BGR2GRAY)` then `cv2.GaussianBlur(gray, (k, k), 0)`,
`k = motion_blur_kernel`. Tested directly rather than inferred: two frames built
from the same base with independent per-pixel random noise (seeded) produce a
smaller mean absolute difference after blurring than the raw grayscale frames do
— the blur's actual job, proven on data built to need it, not just present in the
code.

### Verification performed

- **Exact arithmetic, hand-built frames** (no video encoding, so every assertion
  is exact, not "close enough"): `services/ingestion/tests/test_motion_gate.py`,
  11 tests. Covers: the warm-up window returns `None` for exactly `buffer_frames`
  calls, then scores from the next one; two identical frames score `0.0` and are
  not admitted; **the sharpest test of the ticket's core requirement** — with

- Each of the four numbered design points was checked by breaking it and watching

## OMNI-303 and OMNI-304 · Reworked to Algorithm 1's real shape

### Why this rework happened

OMNI-304's own live check (above) found that CCD clips produce zero gated frames
under the first implementation. The user asked why; the honest answer traced the
cause to a decision OMNI-303 made that was never actually part of Algorithm 1:
sampling one frame per second before gating. A 5-second CCD clip sampled at 1 fps
produces exactly 5 samples, which can never fill a 5-*sample* warm-up buffer — the
bug was in the sampling step, not in the gate. The user then rewrote
`docs/tickets/week-03-04.md` directly: OMNI-303 is now "rework to Algorithm 1's
shape" and OMNI-304 is "ROI-aware spatial-motion sampling," both with re-opened
checklists, and asked for both to be redone and the context notes updated on what
changed. This entry covers both together because the two tickets' changes are
inseparable in the code — the sampling removal (303) is what makes the
time-based buffer (304) able to run on every frame in the first place.

The tickets' own pseudocode (Phase A §3.5.1 / Appendix B.1) was followed line by
line this time, quoted in full in `docs/tickets/week-03-04.md`; every design
choice below cites the line it implements.

### What changed, and why

#### 1. No more sampling — every decoded frame is gated (OMNI-303)

`extract_file` no longer takes an `interval_s`. The `grab()`-and-skip loop that
implemented sampling is gone; every frame `grab()`ed is now `retrieve()`d and
passed to `process_frame`. A 2-minute, 30 fps clip now produces 3,600 rows, one
per decoded frame — confirmed proportionally live (see Verification): CCD's real
5 s/10 fps clip produced exactly 50 rows, UCF-Crime's real 12.9 s/30 fps clip
produced exactly 386.

Grab/retrieve were kept as two separate calls rather than collapsed into
`capture.read()` (which was the first draft) specifically so `retrieve()`
failing after a successful `grab()` still reports "could not decode frame N" as
a real, distinguishable failure, rather than being indistinguishable from a
clean end of file.

#### 2. JPEGs only for admitted frames; a row for every gated one regardless (OMNI-303)

Writing a JPEG for every one of those 3,600 frames is what the old sampling step
existed to avoid, and removing sampling without addressing that would have made
things worse, not better. The fix the ticket specifies: `process_frame` now
writes `frame_path`/`thumb_path` **only when the gate admits the frame**;
otherwise both are `None` and no file is written. A segment row is still created
for *every* decoded frame, admitted or not, with its real `motion_score` —
"rows are cheap, JPEGs are not," and the discarded scores are what keeps the gate
inspectable (needed for OMNI-310's slider). This required making
`segments.frame_path` and `segments.thumb_path` nullable — a migration
(`3f193aff9b39`, combined with the clip-window columns below into one revision,
since both are part of the same rework). The migration's downgrade documents,
rather than works around, the one real limitation this creates: it cannot
re-impose `NOT NULL` on a column that already legitimately holds NULLs.

`services/query/app/extraction.py`'s `segment_file_paths()` (used by both
re-extraction and video delete) was updated to skip `None` entries instead of
turning every row into a path — most rows have none now.

#### 3. `EXTRACT_INTERVAL_S` renamed to `HEARTBEAT_INTERVAL_S` (OMNI-303)

The ticket's own instruction: the setting isn't deleted, its name is freed up for
its real future meaning (OMNI-305's heartbeat — admit a frame on a fixed
schedule regardless of the gate's verdict). Renamed in `services/ingestion/app/
settings.py`, `.env.example`, and the real `.env`. **Not wired to anything yet**
— OMNI-305 wasn't part of this redo, and the setting exists but is unread, same
as `FrameGate`'s placeholder existed unread before OMNI-304's first pass.

#### 4. A stride Δ (a duration) replaces a buffer of samples (OMNI-304)

`MotionGate`'s constructor takes `stride_s` (Δ) instead of `buffer_frames`. The
buffer itself changed shape to match: `deque[(timestamp_s, blurred_frame)]`
instead of a fixed-length `deque(maxlen=N)`. Each call:

- appends the current `(t, frame)` (pseudocode line 1)
- computes `duration = t - buffer[0][0]`; if `< 2Δ`, returns unscored — **2Δ, not
  Δ**, because an admitted frame's clip window (line 7) reaches back to `t-2Δ`,
  so scoring shouldn't start before the buffer has actually seen that much
  history (line 2)
- finds the buffered frame **nearest** `t-Δ` (`min` by absolute time distance),
  not the most recent one, and diffs against it (line 3)
- grid/threshold/count unchanged from the first pass (lines 4-6)
- prunes anything older than `2Δ` off the front, so the buffer never grows
  unbounded regardless of clip length or fps

This is the literal fix for the CCD bug: Δ means the same amount of *time* at any
frame rate, so a 10 fps clip and a 30 fps clip with the same Δ reach the same
verdict — tested directly by running both frame rates over the same real
timeline and asserting identical scores.

`MOTION_BUFFER_FRAMES` is gone from settings, `.env.example` and `.env`;
`MOTION_STRIDE_S` (default **0.5 s**, per the ticket's "defaults to start from")
takes its place. `motion_grid_size`, `motion_cell_threshold`,
`motion_min_active_cells`, `motion_blur_kernel` are unchanged — the ticket marked
these "already built, keep."

#### 5. The causal clip window (OMNI-304, new)

An admitted frame now carries `clip_start_s = t - 2Δ` and `clip_end_s = t` — pure
arithmetic from the frame's own timestamp and Δ, computed once inside
`MotionGate.evaluate()` and threaded through `GateDecision` → `SegmentRecord` →
the ingestion API → `Segment`. Deliberately **not** a lookup into the frame
buffer: the buffer holds preprocessed (grayscale, blurred) frames for
differencing only, never the original bytes a clip would be cut from — the
ticket is explicit that the window is what has to exist now, not 4,500 extra
files, because slice 8 cuts the actual clip bytes from the source video when it
needs them. New nullable `clip_start_s`/`clip_end_s` columns on `segments`, same
migration as the nullable path columns above.

#### 6. The blur deviation, recorded where the ticket asked

OMNI-304's checklist explicitly asks for the blur-before-differencing departure
from the pseudocode to be written down in `docs/results.md`, not just left as a
code comment. Done — see the "Algorithm 1 rework" entry there, dated 2026-09-23.

#### 7. A real bug found while testing the rework, unrelated to the redesign itself

The first version of the new time-based buffer occasionally reported a frame as
unscored (`None`) again **after** scoring had already legitimately started —
comparing floating-point timestamps accumulated from repeated `index / fps`
division against `2 * stride_s` flickers by a few ULPs right at the boundary,
which could make the pruning step remove one entry too many and drop the
buffer's span back under `2Δ` for a call or two. Caught by a test asserting a
`None` score never follows a real one across 50 consecutive calls — the test
failed with 37 scored instead of the expected 46 before the fix. Fixed with a
small (`1e-6` s) epsilon applied asymmetrically to the two boundary comparisons
(the warm-up check is slightly more lenient, the pruning check slightly more
conservative), so the two can never disagree with each other. Re-verified with a
50-call trace showing scoring starts at the expected call and never regresses.

A second, smaller issue surfaced while building the acceptance test itself: a
synthetic "moving" clip built from a sliding block, and then from a freshly
random block per frame, both produced occasional near-zero scores by genuine
coincidence (the shift-per-stride landing under a cell's mean threshold; two
independent random colors landing close to each other). Neither is a pipeline
bug — real footage does show this kind of variation (UCF-Crime's live 31-36
range, not a flat maximum). The test was rewritten to alternate between two
fixed, maximally-different colors by frame parity, which — paired with an odd
frame gap (Δ·fps = 3 here) — guarantees every comparison in that specific test
lands far past threshold, removing the ambiguity for what's meant to be a clean
architecture test.

## OMNI-305 · Heartbeat frames — Algorithm 1 step 5

### Why this ticket exists

Step 5 of the pseudocode OMNI-304 follows line by line: *"also admit a frame at a
fixed interval even when no motion is detected, so parked cars or empty areas
remain represented in the index."* A car parked in a doorway, or any genuinely
static scene, never crosses the motion gate's threshold — without this, such a
recording contributes zero admitted frames for its entire length, no matter how
long it runs. `HEARTBEAT_INTERVAL_S` already existed as a renamed-but-unread
setting since the OMNI-303 rework; this ticket is what actually reads it.

### What was done

Done 2026-09-23, right after the OMNI-303/304 rework, on `slice-03-04-frames-live`.

#### Step 1 — admit a frame every `HEARTBEAT_INTERVAL_S`, regardless of the gate

`HeartbeatGate` in `services/ingestion/app/pipeline.py` **wraps** another gate
rather than replacing it — it forwards a real admission unchanged, and only ever
turns a "not admitted" into an admitted one, never the reverse. `main.py`'s
extraction route now constructs `HeartbeatGate(MotionGate(...), heartbeat_interval_s=
settings.heartbeat_interval_s, stride_s=settings.motion_stride_s)` — one instance
per extraction, same as the gate it wraps, so its own "next one due" clock can
never leak from one video into the next.

The scheduling rule: track `_next_due_s`, starting at `heartbeat_interval_s`
itself (the first heartbeat is due a full interval in, **not at t=0**). Any real
admission — motion or heartbeat — pushes `_next_due_s` forward to
`t + heartbeat_interval_s`, so a motion-rich stretch doesn't also collect
redundant heartbeat admissions right beside its own real ones, and heartbeat
never double-fires for the same due tick.

**A real bug found and fixed before this ever ran:** the first version
initialized `_next_due_s = 0.0`. Since `0.0 >= 0.0`, the very first frame of
every video would have been forced into a heartbeat admission regardless of the
configured interval — caught by a test asserting frames before t=1.0 stay
discarded, which failed with the very first assertion. Fixed by initializing to
`heartbeat_interval_s` instead of `0.0`. Recorded here rather than only in a
commit message, per this sprint's practice of writing down bugs caught before
they reached the running system, not just the ones that didn't.

#### Step 2 — mark the reason; `motion_score` stays whatever it actually was

New shared enum `AdmissionReason` (`motion`, `heartbeat`) in `services/common`,
alongside the other four. `GateDecision` and `SegmentRecord` gained
`admission_reason: str | None`, `None` on a frame that was never admitted at
all. `MotionGate`'s own admission branch now tags itself `"motion"` explicitly
(it previously just set `admitted=True` with nothing distinguishing it).
`HeartbeatGate` passes the wrapped gate's `motion_score` straight through
untouched on a heartbeat admission — including `None`, if the frame was still
inside the motion gate's own warm-up window when heartbeat forced it through.
Tested directly: a scripted inner gate returns `motion_score=None`, and the
heartbeat-admitted decision still carries `None`, not a faked `0.0`.

New `segments.admission_reason` column, nullable enum, migration `70d0558e7c6f`.

**A second real bug, in the migration itself, same class as OMNI-302's:**
autogenerate's first draft was a bare `op.add_column(..., sa.Enum(...))`, which
failed on a fresh database with *type "admission_reason" does not exist* —
`CREATE TABLE` compiles `CREATE TYPE` automatically for an enum column;
`ALTER TABLE ADD COLUMN` does not. Fixed with the standard two-step form:
`postgresql.ENUM(...).create(op.get_bind(), checkfirst=True)` before
`add_column`, with `create_type=False` on the column itself so it isn't created
a second time. The downgrade needed the same `DROP TYPE` fix OMNI-302's
migration needed, for the same reason (`drop_column` doesn't drop the type
either).

#### Step 3 — a heartbeat admission gets its clip window too

Reused `_clip_window(t, stride_s)` — the same `[t-2Δ, t]` arithmetic `MotionGate`
already used, pulled out into a shared helper rather than duplicated. One real
difference from a motion admission: a motion admission can never fire before
`2Δ` (the warm-up guard itself prevents it), so its window is never negative.
**A heartbeat admission can fire during warm-up** — nothing stops it — so
`_clip_window` clamps `clip_start_s` to `0.0`, tested directly with a heartbeat
firing at `t=0.2` against `stride_s=0.5` (an unclamped window would have started
at `-0.8`, before the video even begins).

#### Step 4 — the UI shows the reason: not done, and said so

No frame-facing screen exists yet — OMNI-307 (frames API), 308 (playback) and
309 (frame grid) are all still ahead. `admission_reason` is on every admitted
row, ready for whichever of those reads it first; left unticked in
`docs/tickets/week-03-04.md` rather than checked on the strength of the data
being there.

### Verification performed

- **HeartbeatGate's own scheduling logic, exact and isolated:**
  `services/ingestion/tests/test_heartbeat.py`, 12 tests, using a small scripted
  stand-in gate so the tests depend on nothing about real motion detection.

## OMNI-306 · Re-runnable gating

### Why this ticket exists

The defaults `Δ=0.5s, G=8, τ=25, k=3` are a starting point the plan itself never
claimed was tuned. OMNI-310's threshold slider is what makes tuning them
practical, and this ticket is what the slider actually calls on every drag —
without it, "tune the threshold" means re-uploading the video.

### The decision the ticket asked to be made deliberately

The ticket's own callout says the OMNI-303/304 rework complicates this one:
sampling used to mean every frame had a JPEG, so re-gating could just re-score
whatever was already on disk. After the rework, **most rows have no JPEG at
all** — only admitted (and heartbeat) frames ever get one.

Two options, and the ticket asks for the choice and the reasoning to be written
down:

1. **Re-gate only the frames already on disk.** Fast — no video decode at all.
   But a discarded frame's pixels are gone; there is nothing to re-score. This
   option can only ever **narrow** the admitted set (raise the bar, discard
   more), never widen it
2. **Re-decode the source video and run Algorithm 1 again from scratch**, with
   the new parameters, then update the existing rows in place. Costs the same
   time a first extraction does. Can move the admitted set in either direction

**Decided: option 2, re-decode.** The reasoning is mechanical, not a
preference: OMNI-310's own acceptance is "dragging visibly changes which
frames are admitted" — a slider that only ever discards more as you drag it
one way and can never reveal more as you drag it back is not the slider the
next ticket needs. Option 1 is not a slower, worse version of option 2; it is
a **different, asymmetric operation** that cannot satisfy OMNI-310's
acceptance criterion at all in one direction. There was no real trade-off to
weigh once that was clear — re-decoding was the only option that keeps the
constraint OMNI-306's own checklist names ("the threshold slider in OMNI-310
must stay usable") true in both directions.

### What was done

Done 2026-09-23, right after OMNI-305, on `slice-03-04-frames-live`.

#### Step 1 — re-decodes; updates existing rows, creates none

`POST /videos/{id}/gate` is **synchronous** — the ticket's own sketch shows
`-> {admitted, discarded}` as a direct response, not a status to poll, unlike
`/extract`'s 202-and-poll shape. It reuses ingestion's existing `/extract/file`
route rather than adding a new one: the underlying computation (decode every
frame, gate it, write a JPEG only if admitted) is identical to a first
extraction — only the *parameters* differ. `FileExtractRequest` gained four
optional overrides (`stride_s`, `grid_size`, `cell_threshold`,
`min_active_cells`); any left `None` falls back to ingestion's own settings, so
a plain extraction (which sends none of them) is byte-for-byte the same
request it always was.

Query's side is the part that's actually new: `run_gate()` in
`services/query/app/extraction.py` fetches the video's *existing* segment rows
keyed by `frame_index`, and for each frame ingestion returns, **mutates the
matching row's attributes** (`motion_score`, `admitted`, `clip_start_s`,
`clip_end_s`, `admission_reason`, `frame_path`, `thumb_path`) rather than
deleting and re-inserting. No `db.add()`, no `db.delete()` — the acceptance
criterion ("create no new rows") is true by construction, not by a count check
tacked on afterward. Verified live: the exact same row `id`s and `created_at`
timestamps survived two re-gates on a real clip.

A frame that flips from discarded to admitted (or the reverse) has its file
handled automatically, with no separate cleanup step needed on query's side:
ingestion's `extract_file` already wipes and rewrites the video's whole
`frames`/`thumbs` folder on every call (that behaviour already existed, for
re-running a plain extraction) — a re-gate is just another call to it, so the
files on disk already match the new admitted set by the time query updates the
rows to match.

#### Step 2 — the threshold slider's constraint, satisfied

Live-verified directly, not just argued: extracted a real CCD clip (26
admitted at the defaults), re-gated it with an extreme `min_active_cells=60`
(**4** admitted — only heartbeat's own, motion essentially impossible to
satisfy), then re-gated the same video again with `min_active_cells=1` (**32**
admitted — more than the *original* 26, not just back up to it). A discarded
frame becoming admitted is exactly the direction option 1 could never produce.

#### Step 3 — records the parameters used

New columns on `videos`: `gate_stride_s`, `gate_grid_size`,
`gate_cell_threshold`, `gate_min_active_cells` — one video, one set of numbers
that explains its *current* `admitted` flags, not a log of every run tried.
Migration `2dc384351496`, four plain nullable columns (no enum this time, so
none of `admission_reason`'s `CREATE TYPE` gotcha applied).

Populated by **both** paths, not just re-gating: `_extract()` (a plain
extraction) now also writes these from ingestion's response. The reasoning:
a first extraction is itself one run of Algorithm 1, just at the configured
defaults — "records the parameters used, so a result can be reproduced" is
true of *any* `ready` video, not only one that has since been tuned. Ingestion
echoes back the parameters it actually resolved (after applying any override)
in `FileExtractResponse`, so query never has to independently guess or
duplicate ingestion's own settings defaults to know what was used.

**Not exposed anywhere yet** — `GET /videos/{id}` does not return them. The
ticket's requirement is "records," which persistence satisfies; nothing reads
them back out yet, the same "seam built, not yet surfaced" pattern OMNI-305
left `admission_reason` in.

#### Step 4 — failure handling: revert, don't fail

Extraction's own failure path marks a video `failed` — correct there, because
a fresh extraction that fails leaves the video with no valid segments at all.
Re-gating starts from a video that **already has good segments** from a prior
successful run; failing to recompute them is not a reason to make those
existing, still-valid segments inaccessible. So `/gate` claims the video
(`ready` → `extracting`, the same one-UPDATE-can't-race pattern `/extract`
already uses) and, on any failure — ingestion unreachable, ingestion reports a
real decode problem, or a defensive check described below — **reverts the
video to `ready`**, not `failed`, and leaves every existing segment row
untouched. `videos.error` is not touched by a gate failure either: that column
means "why the video is `failed`," and a gate failure doesn't make it failed.

**A defensive check the ticket didn't ask for, added anyway:** before applying
any update, `run_gate` compares the *set* of `frame_index` values ingestion
returned against the set already in the database. A mismatch (the source file
changed shape since the last extraction, or something is wrong) raises rather
than applying a partial or misaligned update — the same all-or-nothing
philosophy every other write path in this sprint already follows, applied
here because "update rows matched by frame_index" is a new kind of write this
codebase hadn't done before, and it's the one place a silent mismatch would
corrupt data rather than just fail visibly.

A crash *mid*-re-gate (the process dying, not a clean error) is not covered by
the revert-to-ready path above — only a clean exception is. It is still safe,
just less precise: the claim step's own commit already happened, so the video
is stuck at `extracting`; the existing restart sweep (`mark_interrupted_
extractions`, OMNI-303) marks it `failed` on the next startup, same as an
interrupted extraction. The underlying segments are actually still fine in
that case (nothing was committed after the claim), so the practical fix is
just running `/extract` or `/gate` again — a status flag needing a nudge, not
data loss. Recorded here as a known, accepted trade-off rather than solved,
since building finer-grained crash recovery than the rest of this sprint
already has wasn't asked for.

### Verification performed

- **Query's own logic, ingestion faked at the client boundary** (same approach
  as `test_video_extract.py`): `services/query/tests/test_video_gate.py`, 14
  tests. Covers: existing rows updated in place with the same `id` and
  `created_at`, never recreated; two runs at different thresholds give
  different counts and the row count never changes (the literal acceptance
  criterion); a previously-discarded frame becoming admitted, with a real file
  written; `admission_reason`, the clip window and the file paths all correctly
  cleared or set together when a frame's status flips either way; the four
  overrides are forwarded to ingestion exactly, and an omitted one stays
  `None` rather than being defaulted client-side; the resolved parameters are
  recorded on the video, for both a re-gate and a plain extraction; gating
  requires `ready` (refuses `uploaded`, `extracting`); a missing video is 404;
  auth is required; ingestion unavailable, a reported failure, and a
  frame-index mismatch all revert to `ready` with existing segments provably
  untouched, rather than marking the video `failed`
- **Four mutations, each caught by a named, specific set of tests**: replacing
  the in-place update with delete-and-recreate (breaks the same-row-identity

## OMNI-307 · Frames API

### Why this ticket exists

Every ticket before this one wrote segment data; nothing has read it back out.
This is the first API a real screen (OMNI-308's player, OMNI-309's frame grid,
OMNI-310's slider) can actually call, and it is where OMNI-305's own forward
reference — "`admission_reason` is on the row and returned once a frames API
exists to show it" — gets resolved.

### What was done

Done 2026-09-23, right after OMNI-306, on `slice-03-04-frames-live`.

#### Step 1 — filtering in the query, ordered, paginated

`GET /videos/{id}/frames?admitted=true|false|all`, in `services/query/app/
videos.py`. `admitted` is a three-value literal (`Literal["true", "false",
"all"]`), not a plain bool — `"all"` means no filter at all, which a bool
can't express cleanly. Pagination reuses `GET /videos`' exact own convention
from OMNI-207 rather than inventing a new shape: `limit`/`offset`, default 50,
capped at 200. Ordered by `timestamp_s`, matching the ticket's http sketch
exactly.

**A weaker first test caught by mutation-testing itself, not just the code:**
the first version of the "filtering happens in SQL" test built its own
parallel query object and read *its* compiled SQL — which proves SQLAlchemy
*can* express the filter, not that the route's own code does. Mutating the
route to fetch every row and filter in Python still passed all ten tests in
the file, including that one — a false confidence the mutation-testing habit
this sprint has followed throughout exists specifically to catch. Rewrote it
to intercept `sqlalchemy.orm.Query.all()` itself during a real request, so it
captures the exact statement the route's own code sends — that version does
fail against the same mutation. Worth naming here because it is a mistake
about how to *prove* a claim, not about the claim itself, and the whole
practice of "break it and watch a specific test fail" exists to catch exactly
this kind of near-miss.

#### Step 2 — `thumb_url` served by Nginx, never through the API

New `location /thumbs/` block in `infra/nginx/default.conf`, `alias
/data/thumbs/` — Nginx's own `thumb_storage` volume, mounted **read-only**,
and deliberately **not** `frame_storage`: full-resolution frames stay
unreachable from outside the Docker network, only the small thumbnails are
exposed this way. Query builds each `thumb_url` by stripping
`settings.thumbs_path` off the stored `thumb_path` and prepending
`settings.thumb_url_prefix` (`/thumbs`) — a relative path, so it rides
whatever origin already served the page, same as every other same-origin call
this app makes (OMNI-111). `None` on a segment with no file, which is most
rows since OMNI-303's rework.

**The URL prefix is duplicated, not shared, between Nginx and query** — this
project's `nginx.conf` has no templating (no `envsubst`, no settings-driven
generation), so `/thumbs` is a literal in the conf file and a setting
(defaulting to the same string) in Python, kept in sync by convention and a
comment pointing each at the other. This is not a new problem introduced
here: the existing `/api` prefix already has exactly the same three-place
duplication (nginx, `next.config.ts`, `api-client.ts`), documented as an
accepted pattern rather than solved with real templating, which nothing in
this sprint asks for.

**A real gap, named rather than fixed:** thumbnail URLs are **not
authenticated**. Nginx's static-file route has no concept of the JWT this
app's every other endpoint requires — anyone who has (or guesses) a thumbnail
URL can fetch it, unlike every other route in this system. No signed URLs, no
auth-checking reverse proxy in front of the static route exists to close this,
and building one was not asked for by this ticket or any other in this sprint.
Recorded here plainly because it is a genuine, not hypothetical, gap: it is
directly demonstrated in the live check below, where the thumbnail fetch used
no token at all and still returned `200`.

#### Step 3 — `admission_reason`, added beyond the ticket's own sketch

The ticket's literal response shape (`segment_id, frame_index, timestamp_s,
motion_score, admitted, thumb_url`) does not list it. Added anyway, citing
OMNI-305's own note as the reason rather than inventing a new one. This does
**not** tick OMNI-305's fourth checklist item ("the UI shows the reason") —
an API returning a field is not a UI showing it; that box stays unticked
until OMNI-308 or OMNI-309 actually renders something with it.

## OMNI-308 · Playback screen

### Why this ticket exists

OMNI-300 found real dataset footage a browser flatly cannot play: CCD's clips
are MPEG-4 Part 2, and UCF-Crime's carry an extra audio and a PNG-cover-art
stream. Without a browser-friendly copy, opening either from the archive shows
a black box for exactly the footage the sprint's own demo depends on. This is
also the first genuinely frontend-heavy ticket since OMNI-208/209 — everything
from OMNI-300 through OMNI-307 was backend and ingestion work.

### What was done

Done 2026-09-24 on `slice-03-04-frames-live`.

#### Step 1 — ffmpeg in ingestion's own image

`services/ingestion/Dockerfile` installs `ffmpeg` via `apt-get`. The
`opencv-python-headless` wheel already used for probing and gating only
bundles the libraries it links against, not the `ffmpeg`/`ffprobe`
command-line binaries — a separate, real dependency this ticket adds. The
image had to be rebuilt (`docker compose build ingestion`) and the container
recreated, not just reloaded, to pick this up; a plain bind-mount code change
would not have.

#### Step 2 — a playback copy, skipping files already H.264

New `services/ingestion/app/playback.py`, `ensure_playback_copy(path)`. Codec
detection shells out to `ffprobe` rather than parsing OpenCV's own fourcc
encoding — more reliable, and `ffmpeg` is already a hard dependency here for
the transcode step itself. The transcode command is exactly what the ticket
specifies (`-c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p -movflags
+faststart`), written to a `.part` staging file and only `Path.replace()`d
into place on success — the same atomic-write pattern OMNI-205 established for
uploads, applied here for the same reason: a crash or a failed encode must
never leave a corrupt or partial file at the real name.

New ingestion route `POST /playback/file`, called by query right after a
successful probe (`_ensure_playback_copy`, in `services/query/app/videos.py`).
**Deliberately soft-fail, all the way through**: the original file already
proved decodable by the probe that ran moments before, so a video is fully
`ready` and usable for extraction and gating regardless of whether a playback
copy is ever made — a failure here (ingestion down, ffmpeg itself failing) is
logged and swallowed, never raised, and never touches the video's own status
or its `error` column (that column means "why the video is `failed`," and a
playback failure doesn't make it failed).

**Two real bugs found and fixed before this ever ran, both in ingestion's own
tests:**

1. **ffmpeg refused to write to the `.part` staging file at all** —
   `ffmpeg failed: ... use a standard extension for the filename ... Invalid
   argument`. ffmpeg infers the output container from the file's extension;
   `foo.mp4.part` isn't one it recognizes, unlike Python's plain `open()`
   (which the upload path's own `.part` staging relies on and doesn't care
   about extensions at all). Fixed by naming the muxer explicitly (`-f mp4`)
   so the staging suffix stops mattering
2. **The timeout mismatch a first draft would have shipped with:** folding
   playback generation into the *existing* `/probe/file` call would have
   inherited that endpoint's 15-second timeout (`REQUEST_TIMEOUT_S`, sized for
   reading one frame) — nowhere near enough for even a "veryfast" transcode of
   a real recording. Caught by reasoning about it before writing the call, not
   by a failure: `/playback/file` is its own endpoint with its own setting
   (`ingestion_playback_timeout_s`, 150 s), same pattern `/extract/file`
   already established with `ingestion_extract_timeout_s`

**Not caught by a test, named rather than pretended-covered:** the staging
file's actual purpose — atomicity if ffmpeg writes a partial file before
failing — was not exercised. Constructing a real "ffmpeg dies mid-encode"
scenario deterministically (without a flaky kill-the-process setup) wasn't
attempted; the missing-file and corrupt-input failure tests both happen to
fail before ffmpeg ever opens the output, so neither distinguishes staged
writes from direct ones.

#### Step 3 — `videos.playback_path`, a nullable column, and the URL it becomes

Migration `274f8b8dd538`, a single nullable string column — no enum, no
`CREATE TYPE` gotcha this time. `NULL` means either "already H.264, no copy
needed" or "no attempt has succeeded yet"; extraction and gating (OMNI-303/304)
were not touched at all and keep reading `video.path`, the original, exactly
as the ticket requires.

`VideoDetailResponse` gained `playback_url: str` — **not** the raw filesystem
path (OMNI-206 was explicit that no server-side path should ever be exposed),
a relative URL built the identical way `thumb_url` already is (OMNI-307):
strip the storage prefix, prepend a public one. `_video_url()` picks
`playback_path` if set, else `video.path` — always a real, always-servable
answer, whether or not a copy was ever made or attempted.

**A real gap this step's own new code opened, found and fixed in the same
pass:** `DELETE /videos/{id}` predates `playback_path` entirely and only ever
knew how to remove `video.path`. Left as it was, every playback copy this
ticket creates would outlive the video row that claims to own it — a leak
this ticket introduced, not a pre-existing one. Fixed by reading and removing
`playback_path` alongside the original, with a dedicated test
(`test_deleting_a_video_removes_its_playback_copy_too`) that fails cleanly
when the fix is reverted.

**A second thing this step's live check found, about my own process, not the
product:** every earlier ticket's live-verification script this sprint
(OMNI-303 through 307) cleaned up its throwaway video by deleting the ORM
object directly, never by calling the real `DELETE /videos/{id}` — bypassing
its file-cleanup logic every single time. Eighteen orphaned original files had
accumulated on the real `/data/videos` volume with zero matching database
rows by the time this was checked. Removed by hand; this ticket's own live
script was rewritten to call the real endpoint instead, which is also what
proved the `playback_path` deletion gap above.

#### Step 4 — Nginx routes for both new file types, and the gap that comes with them

Two new pieces, mirroring OMNI-307's `/thumbs/` exactly: `location /media/` in
`infra/nginx/default.conf`, `alias /data/videos/`, and `video_storage` mounted
**read-only** into the `nginx` service (it had never needed that volume
before). Nginx's static file serving supports HTTP Range requests natively —
no config needed for that — which is what makes seeking the timeline actually
work; confirmed live below, not assumed.

**The same authentication gap OMNI-307 found, now wider.** `/thumbs/` exposed
small preview images with no token check; `/media/` exposes **entire
recordings** the same way. Nginx's static routes have no concept of this
app's JWT at all. Not fixed — no signed URLs, no auth-checking proxy, not
asked for by this ticket or any other this sprint — but the exposure is
materially larger than OMNI-307's own finding, so it's called out here again
rather than assumed already covered by that earlier note.

#### Step 5 — the player screen

`frontend/src/app/(app)/videos/[id]/page.tsx`, a client component reached by
making the archive table's filename cell a `next/link` (previously plain
text). Uses `useParams()` to read the dynamic segment — this Next.js version
(16.3.4) makes `params` a `Promise` even in Server Components; a Client
Component page can use it directly via the hook instead of threading a
promise through, per the version's own docs (read before writing any code
here, per this repo's `frontend/AGENTS.md` — a real, checked instruction, not
a formality).

Fetches the video (`getVideo`) and its admitted frames (`listAdmittedFrames`,
new API client functions — the first frontend code to call OMNI-307's frames
endpoint at all). The `<video>` element points at `playback_url` directly,
same-origin, no change needed to `api-client.ts`'s request wrapper (a static
media URL isn't a JSON API call). The timeline: a thin bar spanning `0` to
`duration_s`, one small tick per admitted frame positioned by
`timestamp_s / duration_s`, colored by `admission_reason` — indigo for real
motion, amber for heartbeat (OMNI-305) — a small addition beyond the ticket's
bare "marked... visible at a glance" wording, since the reason was already
sitting on every row and distinguishing the two is what actually makes the
shape of the activity legible, not just its presence.

**Deliberately not built:** clicking a timeline tick to seek the player.
OMNI-309 names that behavior explicitly as its own requirement, with its own
callout ("build it properly once," since it returns again in slice 8) — adding
a half-considered version of it here would make decisions (which frames are
clickable, hover previews) that belong to the ticket that actually owns them.

## OMNI-309 · Frame grid with counts

Built on top of the player page from OMNI-308.

**api-client.ts:** replaced the old `listAdmittedFrames` (a single, capped-
at-200 page) with `listAllFrames(videoId, filter)`, which loops
`GET /videos/{id}/frames` past OMNI-307's own 200-row page cap until a short
page comes back. Kept, discarded, and percentage-retained counts have to be
exact, not "however many fit in the first page" — any recording with more
than 200 segments would otherwise silently under-count.

**Single fetch, everything derived client-side:** the player page fetches
`listAllFrames(videoId, "all")` exactly once. The timeline (admitted frames
only), the kept/discarded/percentage counts, and the frame grid's own
filter toggle (admitted/discarded/all) are all derived from that one array
with `useMemo` — switching the grid's filter is instant (no network
round-trip) and the counts can never drift out of sync with what the grid is
showing.

**Frame grid:** a responsive tile grid below the timeline. Each tile shows
the thumbnail (`thumb_url`, served directly by nginx per OMNI-307) or, for a
discarded frame with no thumbnail, a placeholder box labelled "discarded";
a timestamp (mm:ss.t — tenths matter, since a click has to land on the exact
frame) and the motion score underneath; a colored dot (indigo=motion,
amber=heartbeat, matching the timeline's existing convention) on admitted
tiles. Discarded tiles get a dashed border and reduced opacity so the two
states read at a glance.

**Click-to-seek:** a `useRef<HTMLVideoElement>` on the `<video>` element;
each tile's `onClick` sets `videoRef.current.currentTime` directly to the
frame's `timestamp_s`.

**Verified live** (existing test video `Abuse029_x264.mp4`, id 2001, which
had 0 segments — triggered `POST /videos/2001/extract` directly against the
API to get real frame data: 300 segments, 48 admitted / 252 discarded, 16%
retained):
- Counts, thumbnails, timestamps, and motion scores rendered correctly for
  the Admitted view
- Switching to Discarded showed dashed placeholder tiles with the correct
  timestamps and no thumbnail (discarded frames don't get JPEGs, matching
  OMNI-303's original decision)
- Clicked a tile at timestamp 8.833s: confirmed via
  `document.querySelector('video').currentTime` that the player seeked to
  exactly `8.833333`, and the on-screen frame (person walking past the white
  SUV in the driveway) visually matched the clicked thumbnail's content —
  satisfies the ticket's acceptance criterion directly, not just "no errors"
- One red herring during verification: the *first* browser tab's `<video>`
  element got stuck at `readyState 0` / `duration null` indefinitely,
  reproducible even after `video.load()`. A fresh tab loaded the same
  `/media/...mp4` URL instantly (`readyState 4`, correct duration) — nginx's
  Range-request handling was fine the whole time (confirmed via `curl -H
  "Range: ..."`, got a correct `206 Partial Content`). The stuck state was
  specific to that one tab/decoder instance, not a real playback bug — noted
  here so a future "video won't load" report isn't mistaken for a nginx or
  transcode regression before trying a fresh tab first
- `npx tsc --noEmit` and `npx eslint` clean on both touched files (the one
  `tsc` error seen, in `.next/dev/types/validator.ts`, is a stale generated
  file in the gitignored build cache, unrelated to this ticket's source)

Re-extracting video 2001 for this test left it in a clean `ready` state
afterward (300 segments, same as before) — no cleanup needed since it's an
existing test video, not a throwaway upload.

## OMNI-310 · Threshold slider

A slider on the player page, in the Frames section, that re-runs gating for
the recording and updates the timeline, counts and grid together.

**What it controls:** `cell_threshold`, the per-cell motion bar (mean
grayscale difference, 0-255) that OMNI-304's notes named as "the threshold".
`min_active_cells` is the other bar and is left alone. The range is 1-60: on
the test clip everything from 50 up admits the same nine heartbeat frames, so
a wider slider would spend half its travel on no change (sweep in
`docs/results.md`).

**Backend (small):** `GET /videos/{id}` now returns the four recorded gate
parameters (`gate_stride_s`, `gate_grid_size`, `gate_cell_threshold`,
`gate_min_active_cells`). OMNI-306 recorded them but exposed them nowhere; the
slider needs the real current value to start from, not a guessed default. The
frontend `Video` type only takes `gate_cell_threshold`. One new test in
`test_video_gate.py` (detail reports the recorded values and follows a
re-gate); dropping the field from `_to_detail` makes it fail, and restoring it
brings the file back to 15 passing.

**Frontend:** `regateVideo(id, cellThreshold)` in `api-client.ts`, and the
slider in `videos/[id]/page.tsx`. The frames fetch that follows a re-gate
sets the one `allFrames` array that the timeline, the counts and the grid are
all derived from, so they change in the same render by construction.

**Single-flight, latest-wins:** `/gate` refuses a second call while one runs
(409, the OMNI-306 claim), so calling it on every drag event would mostly
fail. While a run is in flight, further drags only update a wanted value;
when the run finishes, one more run goes out for the newest value, and the
loop ends when the applied value equals the wanted one. On an error the slider
snaps back to the last value the server actually applied and shows the
message. A run in flight when the page is left finishes on the server; the
page just stops updating.

**"Does not save to settings":** the slider only ever calls
`POST /videos/{id}/gate`. Nothing writes the `.env`/settings defaults, and no
API for that exists. There is no "save as default" action either: the ticket
says saving is separate and deliberate, but does not ask for it in this
ticket, so it was not built.

**A tension worth knowing about:** `/gate` is not a dry run. Per OMNI-306 it
updates this recording's stored `admitted` flags and the recorded parameters,
so the last position dragged to is what the recording keeps after you leave
the page. "Exploration, not configuration" holds for the settings, not for the
recording's own data. A true preview would need the discarded frames' images,
which do not exist (only admitted frames get JPEGs), so it could not show
thumbnails. Not changed; flagging it in case a "reset to default" is wanted.

### Bugs the browser check found, both fixed

1. **A broken thumbnail after a fast drag.** One tile showed its alt text.
   Every re-gate wipes and rewrites the whole thumbnails folder (OMNI-306), so
   a tile that asked for its image while a following run was rewriting got a
   404, and with an unchanged `src` the `<img>` never asked again. The URL
   returned 200 when fetched afterwards, which is how this was told apart from a
   missing file. Fix: a version counter bumped after each finished re-gate is
   appended to every thumbnail URL (`?v=n`), so the state that stays on screen
   always reloads its images after the last rewrite. Re-ran the burst test
   afterwards: 0 broken of 165. That test shows the fix holds under the same
   kind of burst, but I did not reproduce the original failure on demand, so
   "fixed" rests on the reasoning plus a clean re-run
2. **The 1-60 range edit was not live.** The slider still showed a 100 maximum:
   the dev server was serving code from before the edit, the same bind-mount
   staleness as OMNI-308 (`docker compose restart frontend` fixed it). Along
   the way: the recording had been left at 100 by the first drag, which the
   1-60 slider cannot hold, so the slider now clamps what it shows to its own
   range
