## Why these two merged, and what it costs

Slice 4's own requirement says the live worker must write segments *"through exactly
the same code path as the file extractor, so nothing downstream distinguishes the
source."* Built separately, that means writing the pipeline for files in one week and
retrofitting it for streams the next. Built together, you write it once with two
producers. That is the saving — roughly two to three days.

What does not merge is the UI (playback and frame grid versus live capture status)
and RabbitMQ, which is new infrastructure with its own failure modes. So this is a
**10-day sprint, not a 7-day one.**

**The schedule slips three days.** Slice 5 now starts 30 Sep and everything after it
moves with it. That lands in slice 18, which is a pure buffer week with no scope in
it — which is exactly what the buffer is for. Nothing graded is lost.

---

## The design decision that makes the merge cheap

Keep **"process one frame → write one segment row"** as a single function that knows
nothing about where the frame came from. A file extractor calls it. A live worker
calls it. Nothing downstream can tell the difference — which is what the requirement
asks for, and what makes slices 7 and 8 work on live and uploaded footage without
any special cases.

```
file  ──extract──┐
                 ├──> [ process frame: gate, thumbnail, segment row ] ──> segments
camera ──capture─┘
```

**Part A (days 1–6) calls that function directly, through a background task.
Part B (days 7–10) puts a durable queue in front of it and moves both producers onto
the queue.** Because the function is already isolated, that refactor is small.

Do not start with RabbitMQ. Debugging a broker and a motion-detection algorithm in
the same afternoon is how a week disappears.

## OMNI-303 · Frame extraction — rework to Algorithm 1's shape

> **Reworked 2026-09-23.** The first implementation sampled one frame per second
> and gated the samples. Phase A's Algorithm 1 runs on **every frame**, with a
> per-camera buffer and a stride Δ measured in **time**. The sampling step is not
> in the algorithm, and it is what made all 4,500 CCD clips produce zero gated
> frames. Boxes below are re-opened where the behaviour has to change.

```http
POST /videos/{id}/extract -> {segments_created}
```

**Already correct, keep:**

- [x] `process_frame()` takes a decoded frame plus its source metadata and does not
      know whether it came from a file or a camera
- [x] A thumbnail beside each stored frame
- [x] `/data/frames/{video_id}/…`, `/data/thumbs/{video_id}/…`
- [x] Runs in the background; `extracting` → `ready`
- [x] A mid-extraction failure leaves `failed` with a reason
- [x] Re-running replaces segments rather than duplicating them

**To change:**

- [x] **Decode and gate every frame.** Remove the `interval_s` sampling in
      `extract_file`; `capture.grab()`/`retrieve()` every frame and pass each to
      `process_frame` **[FR-1b]**
- [x] **`EXTRACT_INTERVAL_S` changes meaning** — it is no longer the sampling rate.
      It becomes the heartbeat interval of Algorithm 1 step 5 (OMNI-305). Rename it
      `HEARTBEAT_INTERVAL_S` in settings and `.env.example` so nothing reads the old
      meaning by accident
- [x] **Store a frame and its thumbnail only when the gate admits it**, or when the
      heartbeat fires. Writing a JPEG for every frame of a 30 fps video is not
      affordable at slice 6 scale
- [x] **Write a segment row for every gated frame, admitted or not**, with its
      `motion_score`. Rows are cheap, JPEGs are not — and the discarded scores are
      what make the gate inspectable and the threshold slider possible. Record this
      as a deliberate deviation: the algorithm's goal says "forward only frames with
      meaningful motion", and only admitted frames are forwarded; the extra rows are
      for inspection, not for the pipeline

**Acceptance:** a 5-second CCD clip at 10 fps yields 50 gated frames, not 5. A
2-minute 30 fps clip yields 3,600 rows, with JPEGs only for admitted and heartbeat
frames.

## OMNI-304 · Algorithm 1 — ROI-aware spatial-motion sampling

**Why:** **FR-1b** — *Identify and keep the most informative frames by detecting
movement.* Phase A §3.5.1, pseudocode in Appendix B.1. This ticket follows that
pseudocode line by line; any departure from it is written down with a reason.

**The pseudocode, and what each line requires:**

| Line | Pseudocode | What to build |
|---|---|---|
| in | stride `Δ`, grid `G`, threshold `τ`, min cells `k` | four settings; **Δ is a duration, in seconds** |
| 1 | `Buffer_cam.append(f_t)` | one buffer per camera or per extraction, holding recent frames with their timestamps |
| 2 | `if Buffer.duration < 2Δ: warmup` | warm-up is measured in **time**, not in a count of frames |
| 3 | `diff = \|gray(f_t) − gray(f_{t−Δ})\|` | compare against the buffered frame nearest `t − Δ` |
| 4 | `cells = partition(diff, G×G)` | split the difference image into `G × G` cells |
| 5 | `active = count(c : mean(c) > τ)` | a cell is active when its **mean** difference exceeds `τ` |
| 6 | `if active ≥ k` | admit |
| 7 | `W = Buffer.window([t − 2Δ, t])` | the **causal clip**, 2Δ long, ending at this frame |
| 8 | `forward(f_t, W)` | the frame **and** the clip go forward together |
| 10 | `drop(f_t)` | otherwise discard |

**Already built, keep:**

- [x] Grid partition and active-cell count, `G`, `τ`, `k` all settings
- [x] `motion_score` stored on every gated frame, admitted or not
- [x] One gate instance per extraction, so buffers never cross videos

**To change or add:**

- [x] **Replace `MOTION_BUFFER_FRAMES` with `MOTION_STRIDE_S` (Δ).** A frame count
      means a different duration at every frame rate — it is what broke CCD
- [x] Buffer holds frames covering **at least 2Δ**; warm-up ends when
      `buffer.duration ≥ 2Δ`, per line 2
- [x] Compare against the frame nearest `t − Δ`, per line 3
- [x] Confirm a cell is active on **`mean(cell) > τ`**, exactly as line 5 says
- [x] **Line 7–8, the causal clip.** On admission, record the clip window
      `[t − 2Δ, t]` on the segment. Two new columns, `clip_start_s` and
      `clip_end_s`, and a migration. The clip is cut from the source when it is
      needed rather than written out now — slice 8 encodes it with InternVideo2, so
      the window is what has to exist, not 4,500 extra files
- [x] **Deviation to record:** we blur before differencing; the pseudocode does not.
      It suppresses sensor noise. Keep it, note it in `docs/results.md`

**Defaults to start from:** `Δ = 0.5 s`, `G = 8`, `τ = 25`, `k = 3`. At 10 fps that
compares a frame with one 5 frames back and gives a 1-second clip; at 30 fps, 15
frames back and the same 1-second clip. Same behaviour in time regardless of the
source's frame rate — which is the whole point of Δ being a duration.

**Acceptance:** on a clip that is still and then moves, still frames score low and
are discarded, moving frames score high and are admitted. A CCD clip and a
UCF-Crime clip both produce scored frames. Every admitted segment carries a clip
window of 2Δ ending at its own timestamp.

> **Why grid cells rather than a whole-frame average:** a person crossing one corner
> barely moves a global average but lights up three cells. A global average would
> miss exactly the events this project exists to catch. Have that sentence ready for
> the defense.

## What to learn this sprint

- [Frame differencing and thresholding](https://docs.opencv.org/4.x/d1/dc5/tutorial_background_subtraction.html)
  — the mechanism behind the motion gate.
- [Why grid cells beat a whole-frame average](https://docs.opencv.org/4.x/d7/df3/group__imgproc__motion.html)
  — local motion matters; a global average hides it.
- [Seeking a video element to a timestamp](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/video)
  — central to search and to evidence review later.
- [Reading RTSP continuously](https://docs.opencv.org/4.x/dd/d43/tutorial_py_video_display.html)
  — live capture behaves nothing like reading a file.
- [Reconnection and backoff](https://ffmpeg.org/ffmpeg-protocols.html#rtsp)
  — cameras drop; the system must recover without a restart.
- [Durable queues and acknowledgement](https://www.rabbitmq.com/tutorials)
  — how you get to zero data loss rather than hoping for it.
