## Why these two merged, and what it costs

Slice 4's own requirement says the live worker must write segments *"through exactly
the same code path as the file extractor, so nothing downstream distinguishes the
source."* Built separately, that means writing the pipeline for files in one week and
retrofitting it for streams the next. Built together, you write it once with two
producers. That is the saving — roughly two to three days.

What does not merge is the UI (playback and frame grid versus live capture status)
and RabbitMQ, which is new infrastructure with its own failure modes. So this is a
**10-day sprint, not a 7-day one.**

**The schedule slips three days.** Slice 5 now starts 30 Sep and everything after it
moves with it. That lands in slice 18, which is a pure buffer week with no scope in
it — which is exactly what the buffer is for. Nothing graded is lost.

---

## The design decision that makes the merge cheap

Keep **"process one frame → write one segment row"** as a single function that knows
nothing about where the frame came from. A file extractor calls it. A live worker
calls it. Nothing downstream can tell the difference — which is what the requirement
asks for, and what makes slices 7 and 8 work on live and uploaded footage without
any special cases.

```
file  ──extract──┐
                 ├──> [ process frame: gate, thumbnail, segment row ] ──> segments
camera ──capture─┘
```

**Part A (days 1–6) calls that function directly, through a background task.
Part B (days 7–10) puts a durable queue in front of it and moves both producers onto
the queue.** Because the function is already isolated, that refactor is small.

Do not start with RabbitMQ. Debugging a broker and a motion-detection algorithm in
the same afternoon is how a week disappears.

## OMNI-304 · Algorithm 1 — motion gating

**Why:** **FR-1b** — *Identify and keep the most informative frames by detecting
movement.* Algorithm 1 from the Phase A book, and the heart of the sprint.

1. Compare each frame to an **earlier buffered** frame, not the one immediately
   before — consecutive frames barely differ
2. Divide the difference image into a grid
3. Count the cells showing meaningful change
4. Admit when the count is above a threshold

- [ ] Implemented in ingestion, inside `process_frame()` **[FR-1b]**
- [ ] `grid_size`, `threshold`, `min_active_cells` all parameters from settings
- [ ] **Store `motion_score` on every segment**, admitted or not — this is what makes
      the decision inspectable instead of opaque
- [ ] Grayscale and blur before differencing, so sensor noise is not read as motion
- [ ] Below-threshold frames are stored with `admitted = false` and kept

**Acceptance:** on a clip that is still and then moves, early frames score low and
are discarded, moving frames score high and are admitted — the numbers tell that
story without explanation.

> **Why grid cells rather than a whole-frame average:** a person crossing one corner
> barely moves a global average but lights up three cells. A global average would miss
> exactly the events this project exists to catch. Have that sentence ready for the
> defense.

## OMNI-311 · RabbitMQ, durable queue, acknowledgement

**Why:** **NFR-5** — *On any failure or crash, video or stored data lost = 0.* A
direct call loses whatever was in flight when a worker dies. A durable queue does not.

- [ ] RabbitMQ service in `docker-compose.yml`, config under `infra/rabbitmq/`,
      credentials from `.env`
- [ ] Durable queue and persistent messages — both, or a broker restart loses
      everything **[NFR-5]**
- [ ] The consumer acknowledges **after** the segment row is committed, never before.
      This single choice is what makes "lost = 0" true rather than hoped for
- [ ] Move the file extractor onto the queue too, so both producers use one path
- [ ] Prefetch set, so one consumer does not claim the whole queue

**Acceptance:** kill the consumer mid-run; unacknowledged messages are redelivered
and no segment is lost or duplicated.

## OMNI-314 · Bounded queue and dropped-frame counting

- [ ] Bounded queue: **drop frames rather than accumulating without limit**

- [ ] `fps_effective` and `uptime_s` computed and exposed
- [ ] Dropping is visible in the logs, not silent

**Acceptance:** throttle the consumer deliberately and watch `dropped` climb while

## What to learn this sprint

- [Frame differencing and thresholding](https://docs.opencv.org/4.x/d1/dc5/tutorial_background_subtraction.html)
  — the mechanism behind the motion gate.
- [Why grid cells beat a whole-frame average](https://docs.opencv.org/4.x/d7/df3/group__imgproc__motion.html)
  — local motion matters; a global average hides it.
- [Seeking a video element to a timestamp](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/video)
  — central to search and to evidence review later.
- [Reading RTSP continuously](https://docs.opencv.org/4.x/dd/d43/tutorial_py_video_display.html)
  — live capture behaves nothing like reading a file.
- [Reconnection and backoff](https://ffmpeg.org/ffmpeg-protocols.html#rtsp)
  — cameras drop; the system must recover without a restart.
- [Durable queues and acknowledgement](https://www.rabbitmq.com/tutorials)
  — how you get to zero data loss rather than hoping for it.

> `uv add <pkg> --package omnisight-ingestion` or `--package omnisight-query`, never

> Settings come from `.env` through pydantic-settings. When you are done, show me the
> diff and tell me which acceptance criteria you verified and how.

Four things to insist on this sprint:

- **One `process_frame()`, two producers.** If Claude Code writes a separate live
  path because it is quicker, the merge saving disappears and slices 7 and 8 inherit
  two code paths to special-case.
- **Gating runs from stored frames, never from the video.** If it re-reads the file,
  the slider takes thirty seconds and the feature is dead.
- **Store `motion_score` on discarded frames too.** The instinct is to save space.
  An unexplainable gate is worth far less in the report than a slightly larger table.
- **Acknowledge after the commit, never before.** This is the whole of NFR-5.
