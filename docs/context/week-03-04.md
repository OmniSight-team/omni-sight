## OMNI-300 · Datasets: native layout, local subset, one clip through the app

### Why this ticket exists

Slice 6 loads three datasets through the normal pipeline and derives the lead-up
windows the forecasting model trains on. Its loaders need a written
specification of where every video and every label lives. The ticket started life
as a sprint-2 carry-over asking for a flat layout — each clip's annotation beside
its video, same base name — and was rewritten on 2026-09-21 once the datasets were
actually on disk and it was clear none of them are shaped that way.

### What was done

Work ran 2026-09-20 → 21. All downloading and extraction happened **in Colab,
writing straight to Google Drive** (`MyDrive/omnisight/data/`), not on the laptop:
Colab's network is far faster than a home connection, Drive has 5 TB free, and
Colab mounts Drive for the encoding and training work later anyway. The laptop
only receives a small subset.

#### UCF-Crime — 96 GB, 1,950 videos

**Source:** the official Dropbox folder linked from
<https://www.crcv.ucf.edu/projects/real-world/>. The folder was read directly
before downloading, because the file list first assumed from the project page
was wrong: training normals are **two** archives (35.46 + 31.68 GB), and
`Normal_Videos_for_Event_Recognition.zip` and `Anomaly_Train.txt` had been
missed entirely. Twelve files in total.

**Download:** `wget -c` against each file's Dropbox share link with `dl=1`, in
stages (annotations, then anomalies and test normals, then training normals) so a
dropped Colab runtime never cost more than one file. Every on-disk size matched
the Dropbox listing exactly — Dropbox reports GiB, so 6,272,044,173 bytes appears
as "5.84 GB".

**Extraction:** each archive's structure was inspected with `zipfile` before
writing anything. Every archive has its own single top-level folder, all eight
different, so extracting straight into `videos/` was collision-free. Each extract
printed its mp4 count against the count from inspection:

| Archive | mp4 | Check |
|---|---|---|
| Testing_Normal_Videos | 150 | OK |
| Anomaly-Videos-Part-1 | 200 | OK |
| Anomaly-Videos-Part-2 | 200 | OK |
| Anomaly-Videos-Part-3 | 350 | OK |
| Anomaly-Videos-Part-4 | 200 | OK |
| Normal_Videos_for_Event_Recognition | 50 | OK |
| Training-Normal-Videos-Part-1 | 430 | OK |
| Training-Normal-Videos-Part-2 | 370 | OK |

13 anomaly classes present, 1,950 videos total. Zips deleted only after every
count matched.

#### VIRAT — 37.6 GB, 329 videos

**Source:** the Kitware data portal, which is public — no account or form,
contrary to what the dataset notes had said. Four archives, `videos-00/01/04/05`.
The gap in numbering looked like missing files; it is not. The numbers are
scene-ID groups (`VIRAT_S_00xxxx`, `01xxxx`, `04xxxx`, `05xxxx`) and no scene ID
starts with `02` or `03`. The per-archive listings were read to confirm this
before downloading.

**Extraction:** the first unzip run was interrupted and `videos-00.zip` returned
an error. Re-extracted on its own with `-o`; the folder then held the expected
329.

**Verification:** `md5sum -c viratdata.sums.txt` — **1,236 OK, 0 FAILED.** A first
run of the check reported every file as *FAILED open or read*; that was because it
ran before extraction, against paths inside the zips. Not corruption.

#### DoTA — abandoned, replaced by CCD

The Phase A traffic dataset could not be obtained.

- All three of the author's Google Drive links return 404 — the 55 GB archive, the
  split archives, and the extras folder. GitHub issue #43 has several researchers
  requesting access with no reply
- The repository still ships `DoTA_urls.txt`, the 184 source YouTube videos.
  Every one was probed with `yt-dlp --simulate` from the laptop (YouTube blocks
  Colab's IPs): **0 alive, 184 dead.** A control URL on the same machine resolved
  normally, so it is the dataset, not the tool
- The DoTA **annotations** survive in the repository. Analysing them showed that
  SM-3's Phase A target was never reachable on DoTA regardless: median **3.6 s**
  of footage before the anomaly, and only **8 of 4,677** clips with 15 s or more

Decision: CCD replaces DoTA; SM-3 is reported as mean Time-to-Accident with a
target set from measured data in slice 6, before training. Full write-up in
`docs/results.md`, 2026-09-20. The plan was updated to match (`plan-data.js`,
regenerated `implementation-plan.md`, `docs/datasets.md`), and `data/dota/`
renamed to `data/ccd/`.

**Detour:** the probe needed `yt-dlp`, and the system `pip.exe` launcher pointed
at a Python 3.12 install that no longer exists. Solved with a throwaway uv venv in
the scratch clone (`dota-check/`), kept out of the project workspace.

#### CCD — 6.8 GB, 4,500 videos

**Source:** the Google Drive folder linked from
<https://github.com/Cogito2012/CarCrashDataset>, confirmed live before
downloading. Only the `videos/` folder was taken; the pre-extracted VGG-16
features were skipped since the project builds its own encoders.

**Three problems, three fixes:**

1. `gdown --folder` fetched the three small files and **silently skipped both
   zips.** Fixed by downloading each by file ID with an explicit `-O`
2. `Normal.zip` hit Google Drive's per-file quota — *"Too many users have viewed
   or downloaded this file recently."* Fixed by copying it into our own Drive
   through the Drive API (`files().copy`), which is not subject to that quota,
   then moving it into place
3. **Both archives were first unzipped into the same folder**, and their
   filenames overlap: `Crash-1500.zip` holds `000001–001500.mp4`, `Normal.zip`
   holds `000001–003000.mp4`. Normal extracted second with `-o` and **silently
   overwrote all 1,500 crash clips.** The folder showed 3,000 files and no error.
   Caught by counting per folder; fixed by deleting the mp4s and re-extracting
   each archive with `-d` into its own folder. The zips had not yet been deleted,
   which is the only reason nothing had to be re-downloaded

Final: `Crash-1500/` 1,500, `Normal/` 3,000, plus `Crash-1500.txt`.

#### Step 4 — one clip from each dataset through the app

Done 2026-09-21. The point is to find, on three files, whatever would break when
slice 6 pushes thousands of dataset clips through the same upload path.

**Clips used** (any clip was allowed; these were the first of each in the local
subset):

| Dataset | File |
|---|---|
| CCD | `data/ccd/videos/Crash-1500/000413.mp4` |
| UCF-Crime | `data/ucf_crime/videos/Anomaly-Videos-Part-1/Arson/Arson049_x264.mp4` |
| VIRAT | `data/virat/videos_original/VIRAT_S_010208_07_000768_000791.mp4` |

**1. Source of truth first.** `ffprobe` on each clip before touching the app, so
"matches the source" has something to be compared against. Two things already
showed here: the CCD clip is **MPEG-4 Part 2**, not H.264; and the VIRAT clip is
**23.97 fps and 19 s**, not 30 fps and minutes.

**2. Start the stack.** `docker ps` first failed with *cannot find
dockerDesktopLinuxEngine* — Docker Desktop's processes were running but the engine
was not up yet; it answered a moment later. All containers were `Exited` from
eight days earlier. Started `postgres ingestion query frontend nginx`; `mediamtx`
(the RTSP simulator) is not needed for uploads and was left down.

**3. Predict the result from the app's own probe.** Copied the three clips into
the `ingestion` container and ran `probe_file` from `services/ingestion/app/
file_probe.py` on them, before any UI. It probes with OpenCV (`frame_count / fps`
for duration; width and height from the decoded frame) and returned exactly the
`ffprobe` numbers for all three. Two small tooling detours: bare `python` in the
container has no `cv2` — the service runs from the uv venv, `/workspace/.venv/bin/
python`; and Git Bash rewrote the `container:/tmp/...` half of `docker cp` into a
Windows path until `MSYS_NO_PATHCONV=1` was set.

**4. Get signed in.** The app needs a login and the browser automation does not
type passwords, so the sign-in had to be done by hand. Along the way:

- The database held two accounts, `reviewer@omnisight.local` (admin) and
  `dod-operator@omnisight.local` (operator), both created 2026-09-12 in the same
  second — most likely the sprint-2 fresh-stack demo check. Neither name is in the
  repo or in the week-1/2 notes, and only Argon2 hashes are stored, so their
  passwords were not recoverable
- The seeded `admin@omnisight.local` from OMNI-105 was **not** in the table any
  more. Re-ran the idempotent `scripts/seed_admin.py`, which recreated it from
  `ADMIN_EMAIL` / `ADMIN_PASSWORD` in `.env` and touched nothing else. That admin
  row is still there
- A first sign-in did not help because the login token lives in the browser's
  `localStorage`, which is per browser and per origin. The automation drives its
  own Chrome window, separate from the one already signed in; signing in inside
  that window fixed it

**5. Upload through the Video Archive screen**, one at a time, by setting the
page's file input directly (the native file dialog cannot be driven). Each showed
the green banner *"<name> uploaded — ready"* and a `Ready` row:

| Clip | Screen shows |
|---|---|

| `Arson049_x264.mp4` | 13s · 3.0 MB · Ready |
| `VIRAT_S_010208_07_000768_000791.mp4` | 19s · 1.3 MB · Ready |

**6. Read the stored rows back** with `psql`, because the screen shows only a
rounded duration and size — resolution and fps are not on it. Every stored value
matches `ffprobe` on the source, and `size_bytes` equals the file's byte count:

| id | Stored duration | fps | Resolution | `size_bytes` | Codec |
|---|---|---|---|---|---|
| 32 CCD | 5.000 s | 10 | 640×360 | 232,123 | MPEG-4 Part 2 |
| 33 UCF-Crime | 12.867 s | 30 | 320×240 | 3,142,046 | H.264 Baseline, + AAC audio + 58×38 PNG stream |
| 34 VIRAT | 19.232 s | 23.97 | 1280×720 | 1,362,385 | H.264 Main |

**What differs from a hand-uploaded clip — for slice 6:**

- **CCD is MPEG-4 Part 2.** OpenCV in the container decodes it, so probing works,
  but browsers generally do not play it. The archive screen has no player, so
  playback was **not** tested. If any screen needs to play CCD clips they need
  transcoding to H.264
- **VIRAT is 23.97 fps.** The probe reports the real rate, so nothing breaks;
  slice 6's window arithmetic must use the stored `fps`, never an assumed 30
- **The local clips are short** — VIRAT 19 s, UCF-Crime 12.9 s, against an
  expectation of minutes. Only the local subset was checked (it was built from the
  *smallest* files, which explains it); the full Drive copy was not
- **UCF-Crime carries extra streams** (AAC audio, a PNG). The probe picked the
  H.264 video stream, so no effect
- **The long VIRAT filename squeezes the archive table.** At a 1114 px window the
  Size and Uploaded cells wrap onto two or three lines and the page shows a
  horizontal scrollbar. The cause of the scrollbar was not isolated. All three
  local VIRAT names are this long, so the table needs truncation or a wider
  filename column before VIRAT is loaded in slice 6

**Recorded** in `docs/results.md` as the 2026-09-21 entry "Dataset footage through
the normal upload path" — the evidence behind slice 6's premise that dataset
footage goes through the normal pipeline unchanged.

### Result

All three slice-6 datasets are on Drive and verified: **UCF-Crime 1,950 videos,
CCD 4,500, VIRAT 329.** `docs/dataset-layout.md` describes each in its native
structure, with every number measured rather than assumed. A 38-video subset is
local and untracked by git. One clip from each dataset passes through the normal
upload path and lands `ready` with correct metadata; the differences worth knowing
are CCD's codec, VIRAT's 23.97 fps, and the archive table's handling of long
filenames.

**The pattern worth carrying into slice 6:** in three datasets, the filename alone
lies about identity three different ways — CCD collides across crash and normal,
UCF-Crime collides across two normal folders, and UCF-Crime's split lists omit the
folder level the files actually sit under. The loaders should key every clip on a
path-derived identity, never a bare filename.

## OMNI-301 · Carry-over: retention default

### Why this ticket exists

`videos.retention_until` was created in OMNI-202 but nothing ever wrote to it, so
every row was `NULL`. Slice 16 builds the job that deletes expired footage; with an
empty column that job has nothing to act on and slice 16 would start by fixing
slice 2. An hour now avoids that. The ticket was trimmed on 2026-09-21 to the
retention default alone — the sprint-2 docs and pull-request items it originally
carried are no longer in it.

### What was done

Done 2026-09-21. First checked the ticket's "state found" claim against the code:
`retention_until` appeared only in `models.py`, the response schema, and the
`_to_detail` mapping in `videos.py`, and no setting or `.env.example` key existed.
The claim was right.

#### Step 1 — a retention setting

`services/query/app/settings.py` gained:

```python
# ge=1: the slice-16 retention job deletes footage past this date, so a
# zero or negative value would mark every new upload as already expired.
video_retention_days: int = Field(30, ge=1)
```

The `ge=1` is beyond what the ticket asked for; it is there because a `0` or a
negative value would silently make every new upload expire on arrival, and the job
that acts on it deletes files. `.env.example` gained `VIDEO_RETENTION_DAYS=30` with
a comment saying what it controls. A search for a bare `30` in `services/query/app/`
and `scripts/` finds only that default.

#### Step 2 — set it on every new recording

In `POST /videos/upload`, `created_at` and `retention_until` now come from **one**
Python timestamp and go into the same INSERT:

```python
created_at = datetime.now(UTC)
video = Video(
    ...,
    created_at=created_at,
    retention_until=created_at + timedelta(days=settings.video_retention_days),
)
```

`created_at` used to be a database default (`server_default=now()`). Setting it in
Python instead is what makes "exactly `created_at` plus N days" true by
construction, independent of the database's timezone. One INSERT means no row can
exist without a retention date. The upload is the only place a `Video` row is
created today; slice 4's camera recordings will need the same treatment.

#### Step 3 — backfill

`scripts/backfill_retention.py` runs one `UPDATE videos SET retention_until =
created_at + <days> WHERE retention_until IS NULL`, so a row that already has a
date is never touched — that is what makes it idempotent. It prints how many rows
it changed. Run against the three rows uploaded for OMNI-300 (all `NULL`):

| Run | Rows updated |
|---|---|
| 1 | 3 |
| 2 | 0 |

`SELECT count(*) FROM videos WHERE retention_until IS NULL` went **3 → 0**, and
every row's `retention_until - created_at` is exactly `30 days`.

One behaviour to know about: the date is counted from each row's own `created_at`,
not from today, so a recording older than 30 days comes out already expired and the
slice-16 job will treat it that way. Nothing in the dev database is that old. The
script's docstring says so.

#### Step 4 — tests

`services/query/tests/test_video_retention.py`, three tests, same setup as
`test_video_upload.py` (temp storage directory, probing stubbed to "ingestion
unavailable", a throwaway operator account created and deleted):

- an upload's `retention_until` equals `created_at + timedelta(days=
  settings.video_retention_days)` exactly
- with `video_retention_days` monkeypatched to `7`, a new upload gets 7 days —
  proving the number comes from settings, not a literal
- `GET /videos/{id}` returns a non-null `retention_until`

`uv run pytest` — **65 passed** (62 before, 3 new). The backfill was run *before*
the suite on purpose: the existing upload tests clean up with
`session.query(Video).delete()`, which empties the whole `videos` table in the dev
database, so running pytest first would have deleted the very rows the backfill
needed to be shown on. It did delete the three OMNI-300 demo uploads afterwards.

### Two small detours

- `ruff` flagged the new script's imports as unsorted (`I001`, because the
  `sys.path` insert has to come before the `app.*` imports); fixed with
  `ruff --fix`. The other findings in `videos.py` are the `B008` `Depends(...)`
  pattern already present throughout `services/query/app`
- The first attempt at a live upload found the browser session gone: tokens
  expire after 15 minutes of inactivity (NFR-9), which is the feature working.
  Checked the running `query` container instead (it had hot-reloaded, read
  `video_retention_days = 30`, and contained the new upload code), then repeated
  the upload once signed in again

### Verification performed

- Backfill: 3 rows `NULL` → run 1 updates 3 → run 2 updates 0 → `IS NULL` count 0;
  gap on each row exactly 30 days
- `uv run pytest`: 65 passed; `ruff` clean on every file this ticket touched
  apart from the pre-existing `B008` findings
- **Live, through the Video Archive screen:** `000413.mp4` landed `ready` (row 68)
  with `created_at` 2026-09-21 12:17:15 UTC and `retention_until` 2026-10-21
  12:17:15 UTC — exactly 30 days apart, from the running container

### Result

- `VIDEO_RETENTION_DAYS` (default 30, minimum 1) is the one place the period is
  set; every new upload is stamped with `created_at + that many days` in the same
  INSERT, and existing rows can be filled by an idempotent script
- The column slice 16 needs is populated for every row that exists today
- All checklist items in OMNI-301 are ticked in `docs/tickets/week-03-04.md`
